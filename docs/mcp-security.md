# MCP security configuration

This guide describes the security controls required when exposing a remote MCP
server to Microsoft 365 Copilot. The payroll scenario handles sensitive data, so
the defaults intentionally favor explicit configuration and fail-closed
behavior.

## 1. Security goals

A production MCP service should:

1. Authenticate every `/mcp` request.
2. Accept tokens issued for this API, not merely any valid token from the same
   identity provider.
3. authorize the tenant, user, scope, and requested operation.
4. isolate state and data between users and tenants.
5. protect tokens, client secrets, payroll inputs, and tool outputs.
6. limit network exposure, request size, execution time, and request rate.
7. provide diagnostics without logging credentials or sensitive payloads.

The Microsoft 365 app package is not a security boundary. Users can inspect its
JSON and Markdown files. Store only identifiers and public metadata in the ZIP.

## 2. Recommended token flow: Microsoft Entra SSO

Use Entra SSO when the signed-in Microsoft 365 identity should call your MCP API.
The access token must be issued for the MCP API itself.

### Entra application

Create an Entra application that:

- uses `AzureADMyOrg` for a single-tenant application or
  `AzureADMultipleOrgs` for an ISV application;
- registers the Microsoft 365 Copilot consent redirect URI:
  `https://teams.microsoft.com/api/platform/v1.0/oAuthConsentRedirect`;
- exposes a delegated `access_as_user` scope;
- has `requestedAccessTokenVersion` set to `2`;
- preauthorizes the Microsoft 365 Copilot client for `access_as_user`;
- has an identifier URI matching the value generated by Agents Toolkit.

Microsoft 365 Copilot's client application ID is
`ab3be6b7-f5df-413d-ac2d-abf1e3fd9c0b`.

### OAuthPluginVault registration

`m365agents.yml` uses:

```yaml
- uses: oauth/register
  with:
    name: Contoso Payroll MCP
    flow: authorizationCode
    appId: ${{TEAMS_APP_ID}}
    clientId: ${{AAD_APP_CLIENT_ID}}
    identityProvider: MicrosoftEntra
    baseUrl: ${{MCP_BASE_URL}}
    targetAudience: AnyTenant
    applicableToApps: SpecificApp
  writeToEnvironmentFile:
    configurationId: OAUTH_REGISTRATION_ID
    applicationIdUri: OAUTH_APPLICATION_ID_URI
```

After provisioning, configure the Entra application's identifier URI with the
exact `OAUTH_APPLICATION_ID_URI` value.

### Server validation

Set:

```text
PAYROLL_MCP_REQUIRE_AUTH=true
PAYROLL_MCP_AUTH_MODE=entra
PAYROLL_MCP_ENTRA_TENANT_ID=organizations
PAYROLL_MCP_ENTRA_AUDIENCES=<client-id>,api://<client-id>,<application-id-uri>
PAYROLL_MCP_ENTRA_REQUIRED_SCOPE=access_as_user
PAYROLL_MCP_ENTRA_ALLOWED_TENANTS=<tenant-guid-1>,<tenant-guid-2>
```

Accept all legitimate audience forms that Entra can emit for your application,
but never accept another application's audience. This server verifies:

- `alg` through an explicit RS256 allowlist;
- signature against the token tenant's Microsoft JWKS;
- `iss`, `aud`, `tid`, `exp`, and `nbf` when present;
- the delegated `access_as_user` scope;
- an optional customer-tenant allowlist.

Use `organizations` only with a tenant allowlist unless any Microsoft 365
organization is intentionally allowed to use the service.

## 3. Third-party OAuth

Use `identityProvider: Custom` when users authenticate to a separate service
account or the provider issues opaque access tokens.

Register:

```text
https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect
```

as the provider's authorization-code redirect URI.

Configure the vault with the provider's authorization, token, refresh, and scope
values. Enable PKCE whenever the provider supports it. Keep the client secret in
the Enterprise token store; never place it in the app package or source control.

For opaque tokens, configure:

```text
PAYROLL_MCP_REQUIRE_AUTH=true
PAYROLL_MCP_AUTH_MODE=generic
PAYROLL_MCP_OAUTH_USERINFO_URL=https://identity.example.com/oauth/userinfo
PAYROLL_MCP_OAUTH_SUBJECT_FIELD=sub
PAYROLL_MCP_OAUTH_ALLOWED_SUBJECTS=
```

The userinfo endpoint must:

- use HTTPS;
- reject expired or revoked access tokens;
- return a stable subject;
- describe the same security principal authorized to use the MCP tools.

Do not treat a successful call to an unrelated API, such as Microsoft Graph
`/me`, as proof that the token was issued for your MCP API. Validate the token's
intended resource or use the provider's supported introspection/userinfo design.

## 4. Organization and app restrictions

The OAuth auth config is stored in the Microsoft Enterprise token store.
Microsoft evaluates its restrictions before calling the remote server.

### Organization restriction

- **My organization only**: use for development or an intentionally
  single-tenant deployment.
- **Any Microsoft 365 organization**: required when one package must work in
  external customer tenants.

A cross-tenant package backed by a home-tenant-only registration commonly works
for the publisher and returns a lookup 404 for customers.

### App restriction

- **Existing Teams app ID / SpecificApp**: recommended after the package has a
  stable app ID.
- **Any Teams app / AnyApp**: useful for early development, but unnecessarily
  broad for production.

If the registration is app-bound, the package app ID must match exactly.

### Reference ID

`reference_id` in an API/MCP plugin and `referenceId` in a Cowork connector are
opaque service-issued identifiers. Copy them byte-for-byte. Do not Base64-decode,
reconstruct, or infer a tenant from them.

## 5. Fail-closed server configuration

When `PAYROLL_MCP_REQUIRE_AUTH=true`, startup must fail if required settings are
missing or invalid. A typo must never downgrade the endpoint to anonymous mode.

This repository enforces:

- Entra mode requires a tenant and at least one audience.
- Generic OAuth requires an HTTPS userinfo URL and stable subject field.
- Unsupported auth modes are rejected by configuration validation.
- Authentication errors return a generic 401 response; detailed validation
  reasons remain server-side.

Keep `/healthz` minimal and public. Do not expose configuration, dependency
versions, tokens, tenant IDs, or user information from health endpoints.

## 6. Transport and ingress

Production requirements:

- HTTPS with TLS 1.2 or newer.
- No direct public access to an unencrypted MCP port.
- Host-header allowlisting using the deployed service FQDN.
- Origin allowlisting when browser-originated calls are required.
- Request and response size limits at the ingress.
- Rate limits per tenant and principal.
- Tool execution timeouts below the product's request timeout.
- Web application firewall and DDoS protection appropriate to the risk.

The MCP SDK's DNS-rebinding protection is enabled in this repository. Set:

```text
PAYROLL_MCP_TRANSPORT_SECURITY_ENABLED=true
PAYROLL_MCP_ALLOWED_HOSTS=mcp.example.com
PAYROLL_MCP_ALLOWED_ORIGINS=
```

Origin may be absent for server-to-server requests. CORS is not authentication
and does not protect a public API from non-browser clients.

If a reverse proxy rewrites `Host`, allow only the exact internal host values it
uses. Do not set `*` in production.

## 7. Tenant and user isolation

Never store the "last tool call" in one process-global variable for a
multi-user service. That can expose one customer's data to another caller.

This reference scopes its bounded in-memory demo state by the validated
principal and expires entries. Production services should use:

- a tenant-and-user-qualified key;
- an encrypted data store;
- short TTLs and explicit deletion;
- authorization checks on every read and write;
- regional/data-residency controls where required.

One in-memory replica is used only because this is a demonstration. A scalable
deployment needs an external state store or fully stateless tools.

## 8. Sensitive data and logging

Payroll inputs contain personal and financial data.

- Never log bearer tokens, authorization headers, client secrets, or raw
  timesheet rows.
- Keep `PAYROLL_MCP_DEBUG_TOOL_PAYLOADS=false`.
- Use synthetic data if payload debugging is temporarily enabled.
- Apply log retention, access controls, and regional storage policies.
- Redact identities and values from traces before sharing them with support.
- Do not return more employee data than the requested tool operation requires.

The app package can safely contain an OAuth reference ID, but not the associated
client secret.

## 9. Tool authorization and safety

Authentication answers who is calling; it does not decide what they may do.

For every tool:

- validate input types, ranges, record counts, and encoded file sizes;
- map the caller to an application role or entitlement;
- enforce tenant ownership of every referenced resource;
- mark `readOnlyHint`, `destructiveHint`, and other annotations accurately;
- require product confirmation for write or destructive operations;
- treat files and tool output as untrusted content;
- never allow prompt text to bypass backend authorization.

This demo exposes read-only calculation tools. A real "fund payroll" operation
would require separate authorization, idempotency, approval, audit, and
transaction controls.

## 10. Secrets and lifecycle

- Store OAuth client secrets in the Microsoft Enterprise token store.
- Store service credentials in Azure Key Vault or an equivalent secret manager.
- Prefer certificates or workload identity over long-lived client secrets.
- Rotate secrets and certificates before expiry and test rollover.
- Restrict secret-manager access to the service workload identity.
- Never commit `.env`, generated packages, HAR files, or diagnostic exports.
- Revoke and recreate a vault registration if its secret is exposed.

Deleting and recreating an OAuth auth config produces a new reference ID. Update
the package and increment its version.

## 11. Troubleshooting without weakening security

| Result | Investigation |
| --- | --- |
| 404 before MCP initialization | Vault org/app restriction or stale reference ID |
| Works only in publisher tenant | Change org restriction to Any Microsoft 365 organization |
| App ID mismatch 404 | Compare package app ID with the vault's app binding |
| Repeated sign-in followed by 401 | Check API audience, identifier URI, scope, issuer, and token version |
| 401 from MCP server | Decode only a sanitized token copy; verify `aud`, `iss`, `tid`, `scp`, and expiry |
| 403 from MCP server | Authentication succeeded but application authorization denied the operation |
| MCP endpoint never receives traffic | Stay focused on package/vault provisioning rather than server networking |

Do not disable authentication to diagnose a production connection. Use a
separate nonproduction endpoint and synthetic data.

## 12. Production checklist

- [ ] MCP endpoint is HTTPS-only.
- [ ] Authentication is enabled and startup fails when incomplete.
- [ ] Token signature, issuer, audience, expiry, tenant, and scope are verified.
- [ ] Customer tenants are allowlisted or intentionally open.
- [ ] OAuth vault organization scope matches the distribution model.
- [ ] OAuth vault is bound to the stable Teams app ID.
- [ ] PKCE is enabled when supported.
- [ ] Secrets are stored outside source control and app packages.
- [ ] Host validation, rate limits, timeouts, and body limits are configured.
- [ ] Tool state and data are isolated per tenant and principal.
- [ ] Raw payroll payload logging is disabled.
- [ ] Write tools have authorization, confirmation, idempotency, and audit.
- [ ] Package and OAuth registration rotation procedures are documented.
